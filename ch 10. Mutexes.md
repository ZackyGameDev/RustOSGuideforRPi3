## Motivation

If spinlocks are so simple and they work all the time, why would you need
mutexes?  The answer is simple: a mutex does not keep you hanging.  In spinlock,
when _n_ threads contend for the same lock, only one succeeds in acquiring it,
leaving behind _(n-1)_ threads repeatedly checking whether the lock has become
available, also known as _spinning_.

In a round-robin scheduler, these waiting threads consume entire time slices
doing nothing except repeatedly asking, "Are we there yet?" The answer, for
quite some time is, "No."

Although anything that provides MUTual EXclusion can _technically_ be called a
mutex but in operating systems, the term usually refers specifically to a
**blocking mutual exclusion lock**, such as `pthread_mutex_t`, as opposed to a
spinlock.  By this definition, a mutex must have the following three properties:

1. **Mutual Exclusion**: Only _one_ thread/process can hold it at a time
2. **Sleep**: If another thread tries to acquire it, it _sleeps_ instead of spinning
3. **Wakeup**: When the holder releases the lock, one of the sleepers is awakened.

Don't worry if it does not make sense until now.  Let us derive its
implementation to get a more refined perspective.

## Intuition

In order to build a mutex, we need something that checks whether a lock is held
but instead of checking each time, we just want the thread to _sleep_ if another
process is already working on the critical section. A **critical section** is a
section where concurrent access can lead to non-deterministic behavior so the
part of the program where mutual exclusion is needed. So instead of having the
following:

```
A holds lock

B checks and finds out A holds the lock
Check
Check
Check
Check
...
Finally you can now hold the lock
```

We can instead have

```
A holds the lock

B checks and finds out A already holds the lock
Sleep, essentially waiting for A to release it
```

### The lost wakeup problem
Other than the fact that we don't know how sleep and wakeup are going to work
(yet), there is another problem with this.  What if this happens:

```
(time moves from top to bottom)
A                 B
holds lock
                  looks and finds that the lock is held
releases lock
                  bro went to sleep
```

In this problem, the lock became free before B actually went to sleep.  Nobody
is there to wake B now and it sleeps forever.  This situation is named the _lost
wakeup problem_.

The problem with checking whether the mutex is held and going to sleep are not
atomic.  The lock may become available in the small window between those two
operations, causing wakeup to be missed entirely.  We solve this with a small
internal spinlock.

## The Implementation

### `struct Mutex`

```rs
pub struct Mutex {
    lock: Cell<bool>,
    guard: Spinlock,

    // For debugging:
    name: &'static str,
    pid: Cell<Option<u64>>, // Process holding the lock
}
```

The `guard` is an internal spinlock that protects the mutex's own state.  It is
_not_ the mutex itself; rather, it is to prevent two CPUs from modifying the
structure simultaneously.

`lock` is the mutex's primary state.  The boolean indicates whether the mutex is
currently held.  The `Cell` wrapper is a Rust thing, which lets us modify the
field without requiring a mutable reference to the entire spinlock because
usually Mutexes are passed around as immutable references.

The `name` and `pid` are bookkeeping fields to help us keep debug information.

### The `acquire` function

```rs
pub fn acquire(&self) {
    self.guard.acquire();
    while self.lock.get() {
        // We pass the address of this specific mutex instance as unique wait channel
        Scheduler::sleep(self as *const Mutex as *const (), &self.guard);
    }
    self.lock.set(true);
    if let Some(proc) = Process::get_current() {
        self.pid.set(Some(proc.pid));
    }
    self.guard.release();
}
```

The first step is acquiring the internal `guard`.  Again, this does not mean
that the caller owns the mutex, it simply ensures exclusive access to the
mutex's internal state while we inspect/modify it.

Then, we wait until the mutex becomes free. Once the internal state is protected
from writes, we check whether it is already acquired.  Rather than immediately
failing, the caller waits until the mutex is available.

The `while` is important.  Waking up does not guarantee the mutex is free.
Another thread may have beaten us to it when we were stretching after the nap.

We use the sleep function to sleep on a unique wait channel.  Notice how `sleep()`
takes a reference to the guard.  This allows sleep to release the guard
atomically when putting the thread to sleep, preventing the lost wakeup problem
described earlier.

When execution reaches the point where lock is not held (line 7), either due to
the sleeping thread waking up or the first thread trying to acquire an already
free lock, the current thread marks it as owned.  Since the spinlock is still
held, no other process can simultaneously acquire the mutex.  Ownership changes
atomically from released to acquired.

Then, in the end we do some bookkeeping for debugging, where we record which
process acquired it, releasing the guard in the end.

It should be noted that we did not sleep with the guard held but rather that
sleep is also partly responsible as we will later see.

### The `release` function

```
pub fn release(&self) {
    self.guard.acquire();

    if !self.lock.get() {
        panic!("Mutex release error: ({}) is already unlocked!", self.name);
    }

    if let Some(current_proc) = Process::get_current() {
        if self.pid.get() != Some(current_proc.pid) {
            panic!("Mutex release error: ({}) is owned by PID {:?}, but PID {} tried to release it!",
                   self.name, self.pid.get(), current_proc.pid);
        }
    }
    
    self.lock.set(false);
    self.pid.set(None);

    // Wakeup all processes on this specific Mutex channel
    Scheduler::wakeup(self as *const Mutex as *const ());

    self.guard.release();
}
```

The `release` function functions in a similar way, acquiring the `guard` and
checking if the lock is held in which case it releases the `lock`, clearing up
the debug info and later waking up every thread sleeping on the mutex's wait
channel.  The guard is then released.

Waking all the waiters is simpler than selecting a single waiter.  Although this
can lead to several threads waking simultaneously, only one will acquire the
mutex because they all then compete to hold the internal guard.  This approach
causes the **thundering-herd problem**, which has some performance-degrading
consequences because we wake up many threads unnecessarily only for them to find
the mutex still unavailable. However, for our intents and purposes, the
simplicity of the implementation makes it a reasonable choice.

### Putting a thread to sleep
Now, having understood how the mutex itself works, we can now easily shift our
focus on how sleep and wakeup are actually implemented.

```rs
pub fn sleep(channel: *const (), mutex_guard: &Spinlock) {
        unsafe {
            if let Some(current_process) = &mut PROCESS_TABLE[CURRENT_PROCESS] {
                current_process.set_state(ProcessState::Blocked);
                current_process.chan = channel as u64;
            } else {
                panic!("Scheduler::sleep() was called when no process was active!");
            }

            // Clear Cpu tracker because the process is no longer running
            Cpu::current().clear_current_process();

            mutex_guard.release();

            core::arch::asm!("svc #0");

            mutex_guard.acquire();
        }
}
```

The sleep function simply marks the process state as `BLOCKED` and sets the
channel for the mutex.  The channel is simply a label that tells the kernel what
event a process is waiting for.  For example, a process A might be waiting for a
keyboard, B for a disk operation and C for a mutex.  In the acquire function, we
pass the address of the mutex as the unique identifier for our purposes.

Then, we clear the CPU tracking for the process because it is not running on the
CPU for quite some time.

Notice that the guard is released inside sleep instead of by `Mutex::acquire()`.
This is what makes the operation atomic: once the thread has marked itself as
blocked, it releases the guard and immediately yields to the scheduler.  No
wakeup can be lost in between these two steps.  Finally, we make a call to the
scheduler to schedule something useful while the thread sleeps.  This is
achieved by the `svc #0` call.  When we are woken up by the wakeup call, the
program begins again from line 17, trying to acquire the guard.

```rs
pub fn wakeup(channel: *const ()) {
        let channel_addr = channel as u64;
        unsafe {
            let table_ptr = core::ptr::addr_of_mut!(PROCESS_TABLE) as *mut Option<Process>;
            for i in 0..MAX_PROCESSES {
                let slot = &mut *table_ptr.add(i);
                if let Some(process) = slot {
                    if process.state == ProcessState::Blocked && process.chan == channel_addr {
                        process.set_state(ProcessState::Ready);
                        process.chan = 0;
                    }
                }
            }
        }
}
```

The wakeup call searches the process table for the sleepers sleeping on our
specific mutex channel, marking them as `READY` for the scheduler to
schedule and removing the channel.

The scheduler will eventually choose one of these ready threads to run.  When
that thread resumes execution, it returns from `svc #0`, re-acquires the guard,
and checks the mutex state again.

## Summary

A mutex is essentially a spinlock with the ability to sleep.  The internal
spinlock protects the mutex's own state, while the scheduler provides the
ability to block and later wake waiting threads.  Together they solve the lost
wakeup problem:

1. Acquire the internal guard.
2. If the mutex is free, acquire it.
3. Otherwise, atomically block the thread and release the guard.
4. When another thread releases the mutex, wake the sleepers.
5. The awakened thread re-acquires the guard and checks again.

Although the implementation is only slightly more nuanced than a spinlock, the
behavior is fundamentally different, allowing us to no longer waste CPU cycles
spinning, allowing the scheduler to execute useful work in-between.
